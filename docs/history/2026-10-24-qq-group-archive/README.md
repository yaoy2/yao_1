# 2026-10-24 QQ 群资料归档：过程与续接入口

这次任务的目标是：为用户以后创建的多个 QQ 工作群提供可复用的资料处理能力。接收程序运行在长期使用的电脑 L，各群的新消息、文本和文件分别保存到用户指定的 Google Drive 同步目录，再由电脑 D 查阅和核验。每个工作群独立授权、独立启用、独立归档，普通消息不必每次都 `@` 机器人。

**截至 2026-10-24，原接收程序和多群归档副本已分别完成离线验证，但尚未在 L 安装、扫码或启动；没有新建机器人，真实群归档尚未通过验收。** 当前阻塞是 L 的 WorkBuddy 安全中心拒绝读取部署文件，且本次拒绝没有可在手机 QQ 批准的待审批请求。用户暂时无法操作 L，因此要求把前因后果和后续工作归入仓库。整理后的可复用副本以它自己的清单与验证记录为准。

## 两类问题需要分开处理

### 1. QQ 消息接收链路

腾讯协议已定义 `GROUP_MESSAGE_CREATE`，用于接收群内普通消息。当天查看的 WorkBuddy 5.8.3 本机代码将这类事件标为未提及机器人，而默认提及过滤会跳过未提及消息；L 的版本由用户报告为 5.8.3.0。这与受控群测试相符，是较强的原因线索，但没有在 L 取得原始事件日志，**不能写成已证明 L 的全部根因**。

另一个独立问题是，腾讯官方 Python 包 `qqbot-agent-sdk==1.2.2` 的默认消息分发列表也未包含 `GROUP_MESSAGE_CREATE`。本次程序采用项目内局部子类保留该原始事件，复用 SDK 的扫码、鉴权、心跳与重连；没有改动全局 SDK 或 WorkBuddy 安装文件。真实 SDK 的原始事件分发已通过离线测试，仍需真实 QQ 推送验收。

用户报告刚完成个人认证，但旧机器人管理页当时仍显示未认证主体。主体归属、认证生效和旧机器人权限的关系没有查明，不能断言“重新创建就一定解决认证问题”。

### 2. L 的部署文件读取权限

安装指令到达 L，目标机器与文件同步状态均已核对。`Get-FileHash` 运行时，文件访问返回拒绝，工具同时标注命中 Security Center 规则并要求不得重试或采用等效替代。后续诊断未发现可通过 QQ 批准的待审批请求。

这与 QQ 平台消息权限、机器人认证是两件事。必须先由用户通过 L 的正常安全中心入口处理所需目录授权，再核对权限状态并继续部署；不能使用 D 计算出的哈希替代 L 的文件读取检查，更不能把“可以写报告”推断为“可以读取或执行安装脚本”。

## 程序归档与多群目标

当天冻结的原接收程序包含 `archive_engine.py`、`qq_service.py`、`bootstrap.ps1`、`requirements.txt`、测试和说明。归档包使用去除群专属默认值后的可复用副本，版本标识为 `20261024-archive-multigroup-1`；原始文件留在原位置保留证据。两者不能宣称字节完全一致，也不能混用旧冻结哈希。主包使用 `manifest.json`，归档版代码使用 `source/release-manifest.json`。继续部署应以实际取回版本的清单、配置参数和相应验证记录为准。

程序设计按授权群和日期分别保存消息来源、附件状态及文件索引，按消息 ID 去重。附件下载后核对字节数和 SHA256；短暂失败最多进行三次补存。未授权群的正文不归档，聊天内容不能触发任意脚本或文件读取。凭证计划仅在 L 本机使用 Windows DPAPI 保存，不进入同步目录。

每个新工作群都需要单独完成入群权限和启用流程，不能因机器人已在一个群可用，就推定其他群已获授权。群内状态、搜索、文件列表与整理命令必须限制在发起命令的群内；多群并行接收及跨群隔离仍需实机验收。

目前的“整理”是消息计数、文件清单和原文线索摘录，**没有实现 AI 语义摘要**。如要进一步形成讨论摘要、明确决定和可靠待办，还需另行设计与验收，不能把索引生成当成这些能力已经完成。

## 继续时不要重走的路

- 不以“已开启接收全部消息”“已收到某条私聊”或“生成了一份报告”代替普通群消息和实际附件验收。
- 不在 D 绑定新服务，不把任何非 D 机器自动视为 L。
- 不在替代方案验收前切换或删除旧机器人。旧机器人仍是已有的 L 操作通道。
- 不复制账号凭证到聊天、同步目录或仓库；不点击可能重置密钥的入口来做只读检查。
- 不因权限拒绝改用另一命令、内联脚本、复制路径、关闭保护或更宽权限模式。
- 不将缺失发送者、时间、附件下载结果或历史消息补成看似完整的记录。
