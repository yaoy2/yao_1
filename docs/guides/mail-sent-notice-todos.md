# 已发送通知的待办提取规则

只通过获准的 Edge 浏览器界面，从已发送的通知中提取有明确时间和具体动作的待办。通知正文与可在线预览的非会议纪要附件都可以提供依据；收件箱、待发送的发件箱和会议纪要不在读取范围内。邮件和附件不下载到本地。本规则替代此前的本地邮件读取、附件下载解析，以及将周期制度、笼统计划和待核对事项一并列为待办的做法。

## 读取边界

- 唯一主路径是 CUA 或平台允许的 Edge 界面控制，在本人已经登录的学校邮箱中操作。只选择明确识别为“已发送”的邮件目录；找不到时报告缺口，不能回退到收件箱。
- 打开正文前先检查邮件主题，打开附件预览前先检查附件名。命中会议纪要、会议记录等排除名称时，仅保留必要的排除状态，不打开、读取、解析或归档其内容。
- 普通附件只用邮箱网页提供的在线预览，不点击“下载”或“全部下载”，不另存邮件，不建立本地附件副本。在线 Excel 预览先检查可见工作表名，不打开会议纪要工作表。明确标注为示例、样例或范例的表格与行不作为真实通知要求；已填写的表格不能仅因文件名含“模板”而整体排除。
- 一份独立通知可以要求收件人提交“培训纪要”等材料；这只是待交材料名称，不代表允许打开实际纪要文件。若邮件主题或附件名本身命中纪要排除规则，仍按读取边界排除。
- 无法在线预览的附件只报告“未读取”及具体缺口，不据此建立待办，也不能声称其中没有任务。需要下载才能查看的压缩包、扫描件或其他格式均遵循这一规则。
- 不转用 HTTP 请求、IMAP、本地 Foxmail、已有本地邮件副本或其他下载解析方式兜底。登录过期、账号选择、MFA 或平台要求本人完成的步骤由本人处理；缺少工具或预览能力不扩大读取授权。

## 进入待办的条件

一项要求必须同时说清“何时”和“交什么材料或做什么具体事情”，并有已发送通知或允许读取的附件作为直接依据。

时间可以是具体日期，也可以是能由邮件发送日期可靠确定的相对日期，例如通知明确写出的“本月底前”。有原文时刻时保留时刻；只有日期时保留日期，不擅自补成 17:00 或下班前。查询今天之后的事项时，以本次查询日期判断范围，并将今天到期的事项单独表达。下面六项接受例子是判断明确程度的标准，不能把示例本身当作另一封邮件的事实依据。

具体日期的执行安排可以进入待办，不限于材料提交。例如已报送的培训计划明确写出“10月9日开展经验分享”，待办是到日开展活动，不是重新提交已经报送的计划。条件性要求保留原条件，例如“如继续聘用，10月8日前提交审批材料”。

以下内容不进入待办：只有“每周”“每月”“每学期”等周期而没有具体当期日期的制度要求；模板示例；日期互相冲突、无法确定或需要核对的事项；只有方向、目标或大致月份的笼统计划。不能从惯例、例会纪要或模型推测中补日期、时刻、责任人或材料。

同一任务在正文和附件中重复出现时应合并依据。已经报送某个计划，不等于其中尚未到日的执行事项已完成；也不能在未核实完成状态时声称接收人尚未完成任务。

## 六项接受例子

以下例子依据已确认的六项截图内容改写为通用角色，不包含个人邮箱。时间只有日期，均不添加通知原文没有的时刻。

| 通知中的明确要求 | 应生成的具体待办 | 必须保留的边界 |
| --- | --- | --- |
| 9月30日前完成课程思政问卷并提交完成截图 | 完成问卷并提交截图；截止9月30日 | 材料是完成截图，不能扩展为另交总结 |
| 9月底前，各管理中心梳理、量化和分解年度指标，报分管负责人审定 | 完成年度指标梳理、量化和分解并报审；截止9月底 | 保留报审动作与接收角色 |
| 如继续聘用，10月8日前提交退休返聘审批材料至人力资源部门 | 条件满足时完成并报送返聘审批材料；截止10月8日 | 保留“如继续聘用”，不把条件性任务改成无条件要求 |
| 第二阶段培训计划明确安排10月9日线下开展1次优秀教师、优秀教师新锐经验分享 | 10月9日组织线下经验分享1次 | 这是有具体日期的执行事项；已经报送的计划不重复列为提交任务 |
| 10月27日前，学院月报经审核后报党政办公室，并抄送院领导 | 审核并报送当期学院月报；截止10月27日 | 日期必须来自明确的当期要求；不能只凭“每月27日前”泛化出这项任务 |
| 12月31日前提交新进教职工培训总结、签到表、PPT、培训纪要和图片 | 汇总并提交列明的培训材料；截止12月31日 | “培训纪要”只是待交材料名称，实际纪要内容仍不读取 |

对照排除例子：“每周五报送”“每个教学周至少巡课1次”“理论学期至少听课5次”属于没有具体当期日期的周期要求，不加入待办；“12月上旬计划考试”“名单10月前／10月底前”也不能被加工成确定截止任务。示例表格内的日期和动作不能当作已发送通知的真实要求。

## 代码入口与在线资料

执行自动化的 Codex 通过获准的 Edge 工具完成网页操作；仓库的 `utils/mail_manual_review.py` 只接收在内存中的在线观察结果，并不是独立的浏览器登录器。每封输入必须标明 `source_transport="edge"`、无凭据及查询参数的学校邮箱 `source_url`、`folder="已发送"`、页面显示的发信时间 `sent_at`，以及实际看到的正文和允许的附件预览文字。不得传入本地路径、原始邮件或附件二进制。

批次 `window.through` 应为本次在线检查时刻，用于过滤当天之前已经到期的要求；不以发信时间代替当前检查日期。不提供有效检查时刻时，调用方必须先限定今天及以后的范围。未预览或未完整预览的附件必须如实记录读取状态，不能假装已经读取。

旧 `mail_imap_collect` 收信入口、`mail_imap_setup` 认证入口以及 `mail_filing_source.read_source` 原件补取入口已被代码阻止；它们不会成为 Edge 失败后的替代路径。旧内部实现仅保留作兼容和虚构数据回归测试。原邮件工作台的“立即收信”不负责启动 Edge；当前邮件待办应按本文由 Codex 的 Edge 工具执行。

## M14 去重与完成状态

按已有授权写入 M14 前，先查现有事项，用通知来源、具体动作和日期识别同一任务。已有任务不重复新增；正文、在线附件以及重发通知对同一事项的补充只合并证据，不制造多条待办。

保留用户在 M14 中设置的完成状态及已有人工处理结果。重新抓取、重新整理或日期到来都不能把用户已完成的任务改回未完成；有差异时呈现证据，由用户决定是否调整。本说明本身不扩大 M14 写入授权。

## 本机状态与另一台电脑接手

本机自动化状态为 **PAUSED**，保持停用。更新仓库说明不创建、不启用本机任务，也不自动读取真实邮件。

L 在自己的电脑拉取代码后，先阅读本仓库这份说明，另行核对本机 Edge 控制能力、邮箱账号和已发送目录等设置。邮箱登录、账号选择及必要验证由本人完成；不能复用另一台电脑的登录状态、凭据或任务启用状态。

先由本人选择小范围已发送通知做只读测试，核对主题和附件名排除、在线预览能力、原文日期、具体动作与 M14 去重结果。测试仍不得下载邮件或附件。通过测试不自动启用定时采集，不启用当前电脑的任务；L 如需自动化，应在其本机另行明确设置和授权。
