## 按这个顺序继续

### 1. 确认 L 的环境和读取权限

在用户确认的 L 上核对真实主机、现有 Python、部署目录和当前服务状态。此前已确认存在 Python 3.14；实际路径应从当前 L 环境核实，不要假设旧记录现在仍未变化。

由用户在 L 的 WorkBuddy 正常安全中心界面处理本次服务目录的读取权限，保持其他保护。然后重新核对本次 `bootstrap.ps1` 和 `release-manifest.json` 的 SHA256。若仍收到明确拒绝，停止该动作，记录准确原因；不使用 D 上的校验值代替 L 的读取，也不跳过清单校验。

### 2. 核对已有状态，再准备本机隔离环境

检查是否已有本服务的运行版本、凭证或接收进程。首发脚本遇到已有运行版本会停止，不要通过删掉记录、覆盖凭证或结束进程来强行重装；先确认这些状态是不是后续操作已经产生的。

以下是参数结构。具体值从当前 L 环境和用户确认的归档要求取得，**不要原样运行占位符**：

```powershell
$sourceDir = '<L 上已核实的服务源码目录>'
$archiveRoot = '<用户指定的归档同步目录>'
$expectedHost = '<已确认属于 L 的实际主机名>'
$pythonExe = '<L 已安装的 Python 完整路径>'
$manifestSha = '<本次核对的 release-manifest.json SHA256>'
$bootstrap = Join-Path $sourceDir 'bootstrap.ps1'

& $bootstrap -Mode prepare -SourcePath $sourceDir -ArchiveRoot $archiveRoot -ExpectedHost $expectedHost -PythonExe $pythonExe -ExpectedManifestSha256 $manifestSha
```

`prepare` 会复制通过校验的程序到 L 本机并新建专用 Python 环境。只有明确返回成功，才进入下一步。不修改 PowerShell 执行策略，不安装全局 Python，不设置开机任务。

### 3. 生成二维码，由用户选择新机器人

```powershell
& $bootstrap -Mode onboard -ArchiveRoot $archiveRoot -ExpectedHost $expectedHost
```

仅首次尚未完成绑定时执行本步骤；已有本机凭证和成功回执时不再扫码。读取本次新生成的 `onboarding.json`、二维码时间、对应进程和错误记录，确认扫码任务仍有效。当前版本在扫码过期后可能保留旧的 `awaiting_scan` 状态，应结合 `startup_error.json` 的本次时间判断，不能继续使用过期二维码。用户用 QQ 扫码，在官方页面选择 **创建新机器人**；若本轮新机器人已经创建，则选择该新机器人，并核对使用的主体。选择旧的在线机器人可能断开原来的 WorkBuddy 连接；即使配置了旧机器人检查，也不能撤销平台上已经发生的切换。

等待 `onboarding.json` 明确显示 `completed`。凭证仅由官方扫码流程交给 L 本机程序，并使用 Windows DPAPI 保存；不得把 AppSecret、令牌或凭证文件发到聊天、放进同步目录或提交 GitHub。

### 4. 启动接收，逐个启用工作群

```powershell
& $bootstrap -Mode start -ArchiveRoot $archiveRoot -ExpectedHost $expectedHost
& $bootstrap -Mode pair -ArchiveRoot $archiveRoot -ExpectedHost $expectedHost -GroupName '<已确认的目标群名称>' -GroupNumber '<已确认的目标群号>'
```

由用户把新机器人加入当前要启用的工作群，并在 QQ 的机器人权限中开启接收群内全部消息。每个工作群单独生成一次 `pair` 启用指令，在有效期内仅用于对应的群；按当前 QQ 权限要求使用真正的机器人提及。完成一个群的绑定并核对结果后，再为下一个群生成新指令。真实 `group_openid` 来自实际事件，不能由显示群号猜测。

维护各群独立的启用状态和归档目录。未启用的群不保存正文；任何群内查询、文件列表或整理结果都不得包含其他群资料。新增群、停用某个群和调整群级权限均应明确操作范围，不把一个群的授权扩展到所有群。

确认本次 `health.json` 显示连接成功，并检查心跳和更新时间。旧的状态文件、进程启动返回值或平台显示“在线”，均不能替代下一步的消息和附件验收。

### 5. 完成真实群验收

| 检查 | 必须核对的结果 |
| --- | --- |
| 用户普通消息，不 `@` 机器人 | 出现在按群、日期保存的原始记录中；正文、发送者、时间和来源 ID 有实际证据 |
| 另一位群成员普通消息 | 同样能归档，不能只用创建者自身消息推断所有群成员可用 |
| 一份新的测试文件 | 文件真实下载；原名、字节数和 SHA256 与发送前独立记录一致；不能仅有附件名称或链接 |
| 一张图片 | 文件实际保存且能打开，消息与图片来源对应 |
| `归档状态` | 数量与实际记录一致，失败附件明确计入未保存数量 |
| `文件列表` | 显示实际收到的文件，已保存与未保存状态准确 |
| `查找 关键词` | 返回有来源的原文摘录，不编造匹配内容 |
| `整理今天` | 生成当天资料索引和原文线索，路径可回读 |
| D 端回读 | 经 Google Drive 到达 D 的文件内容、字节数和 SHA256 与 L 的归档相符 |
| 至少两个测试工作群 | 各自独立启用、收到的消息和文件分开归档；同名文件不会混入别的群 |
| 跨群查询隔离 | 在一个群查询另一个群专用的测试关键词时，不得返回其他群的消息、文件或整理内容 |
| 未启用的测试群 | 不写入该群正文或附件，不能因机器人已入群而视为自动获准归档 |
| 重复与恢复 | 在获准的测试方式下核对重复事件不重复计数、短暂失败能恢复；未实际测过的恢复场景明确标记 |

全部测试使用新建的无私人信息材料，不复述此前实际群内信息；测试文件先独立记录字节数与哈希。不要把预期内容和哈希交给执行端后，只凭其复述就认定通过。群友参与、QQ 平台未推送或其他无法完成的项目应保持待验收状态。

### 6. 再处理长期运行和旧机器人

首个群的核心接收验收已通过。当前已准备 `run-current.ps1` 和登录自启任务定义，但尚未注册任务：拟由当前用户登录后启动，异常退出每分钟重试，最多 999 次；不保存密码，不承诺注销后继续运行。入口会先核对主机、当前发布清单与文件哈希，并等待接收进程退出，使计划任务能取得真实退出状态。启用前核对用户对该系统任务的确认；启用后需实际从任务启动并回读新进程和心跳，不能只凭任务注册成功报告运行正常。

在新方案通过验收、确认原 WorkBuddy 通道不再需要后，才能按用户的具体授权处理旧机器人；平台若要求删除时由用户确认，按正常流程完成。不要把此前允许“可以新开、删旧的”理解为可以在替代服务未可用时切断唯一远程通道。

## 已知实现边界

- 本版固定使用 `qqbot-agent-sdk==1.2.2`。官方包当时默认未分发 `GROUP_MESSAGE_CREATE`，项目内局部子类专门保留该事件；升级 SDK 时重新核对这条接口，不盲目移除修正。
- 授权群的原始输入先存入 L 本机，再写入同步归档。临时归档失败会退避重试，重启恢复待处理输入；附件短暂失败按约 10、30、90 秒重试，最多三次。
- 默认单附件上限为 200 MiB，超限或无法保存会留下明确状态。平台文件类型、链接有效期和特殊转发内容仍以实测为准。
- 只保存实际推送的新消息，不补采入群前历史，不保证还原旧群文件库、编辑、撤回和平台未推送的转发细节。
- 当前整理是计数、文件清单和原文线索摘录，没有模型接口，不是 AI 语义摘要。如继续实现讨论摘要、决定和待办提炼，应在已有可追溯原文上另行设计和验收。
- 本版不执行聊天中的任意命令，不允许借机器人读取任意本机文件，也不自动删除或群发。
